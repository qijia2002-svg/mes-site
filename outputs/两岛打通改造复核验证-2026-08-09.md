## ✅ P0：`sim_*` 表没有任何判题练习 —— 确认

**证据（全仓检索 `sim_work_orders|sim_production_records|sim_quality_checks`）：**
- 命中文件仅：`simToSql.ts`（序列化器）、`dataset.ts`（样例查询 `SIM_SAMPLE_QUERY`）、`docs/*`（设计文档）、`tmp/*`、以及**构建产物** `dist/assets/*.js`。
- `docs/seeds/*`：**0 命中** —— 没有任何 `sql_exercises` 种子引用 `sim_*` 表。
- `worker/src`：**0 命中**。
- `SandboxChallenge`：仅出现在 `SqlSandbox.tsx` + `dataset.ts`（**UI 包装组件，无数据模型、无种子**）—— 没有围绕 `sim_*` 的挑战模板。
- 线上复证：尝试 `node scripts/lib/d1.mjs query "SELECT ... sql_exercises WHERE answer_sql LIKE '%sim_%'"`，但非交互 shell 缺 `CLOUDFLARE_API_TOKEN`（wrangler 报错），未能直连。源码级证据已充分，与审查中"D1 查询 0 行"一致。

**判定**：数据层（`simToSql` 序列化，命名空间隔离、单引号转义、不碰 canonical 表）与 UI 层（双模式切换 + 预置示例查询 `SELECT ... FROM sim_work_orders`）都接上了，但**没有一道正式题目/挑战让学生对"我自己那条线"练 SQL**。差异化卖点"我搭的线，我自己查"在任务层是断的——学生送完数据，除了看一眼示例查询，无事可做。

**修复方向**：在 `sql_exercises` 加 1–2 道围绕 `sim_*` 表的题（如"查我本轮仿真各工序的不良分布""对比计划合格产量与实际合格产量"），`answer_sql` 查 `sim_work_orders`/`sim_production_records`/`sim_quality_checks`；哈希按归一化算法在 `dataset.sql` 同源算（注意 `sim_*` 是运行时追加，`--regress` 需先 `useSandboxDb` 注入 sim SQL 再算，或基于固定 snapshot）。或至少补 `SandboxChallenge` 模板引导。

## ✅ P1：WIP 默认不触发 —— 确认（且比原描述更严重）

**证据链：**
1. `simReducer.ts:17` `createNode` 返回 `props: {}` —— 拖出来的节点无任何 `hours`/`capacity`/`defectRate`。
2. `simScenario.ts:66` `buildGenericFactory` 的 12 个默认节点**也走 `createNode`** → 默认通用工厂 12 节点全部 `props:{}`。
3. `simEngine.ts:442-446` 产能计算：`cap = capacity>0 ? capacity : hours>0 ? 60/hours : Infinity`。
   - 因为默认节点 `hours` 缺失 → **所有节点 `cap = Infinity`** → `through = Infinity` → `wip[node] = 0`（`:449`）。
4. `simEngine.ts:419-433` 瓶颈检测：`minCap` 初值 `Infinity`，遍历中只有 `cap < minCap` 才更新；全 `Infinity` 时**永不更新** → `bottleneck = null`。
5. `simLevelDefs.ts:100` 第 4 关验收含 `{ label:'已识别瓶颈工序', ok: !!bottleneck }` → **默认节点下该检查恒为 false**，第 4 关不可通过。

**判定**：原审查说"手动把某节点产能设得极低（<12.5 件/小时）才会冒 WIP"——正确，但遗漏了**默认场景同样全 Infinity**。即开箱即用的通用工厂，WIP 徽章/拥堵边/瓶颈描边**全都不显示**，第 4 关的"已识别瓶颈"检查也永远不过。这个重金做的可视化功能在默认体验里形同虚设，不只是"手动搭线"才失效。

**修复方向**：
- 给 `NODE_LIBRARY` 各工序一个合理的默认 `hours`（如 5–8 分 → 产能 7.5–12 件/时），使默认场景自然出现一个瓶颈 + WIP 堆叠；**或**
- 第 4 关预置一条带明显瓶颈的模板线（在 `buildGenericFactory` 之外另建 `buildBottleneckLevel()` 预设，给某一节点设低 `capacity`）。
- 同时重算第 4 关阈值（见下方 🆕 发现，当前 260 不可达）。

## ✅ P2：关卡通过没回写闭环（无条件派发）—— 确认（精确措辞）

**证据链：**
- `SimulatorPage.tsx:251-256` 派发 `NODE_RESOURCE_DONE` 的守卫只有 `if (from && SIM_REF_ID[from])` —— 即"从流程节点 `?from=` 进入"即派发。
- `:183-195` 在 `!result.ok` 时 `setRun(...错误...) + return` 早退 —— **所以失败的运行不会派发**（审查原文"仿真成功后……不论当前关卡验收是否通过"措辞精确，没有夸成"连失败都派发"）。
- 因此缺口是：**仿真成功（`ok=true`）但当前关卡验收 `pass=false` 时，仍派发 `NODE_RESOURCE_DONE`** → `factory.progress` 把该流程节点的 sim 实战标记为"已完成"。
- 原架构记忆写过原则是"只认做过实战"，但审查主张语义应为"通过挑战才计完成"——这是设计意图的选择，但"成功但烂线也计完成"明显偏离"通过挑战"。

**修复方向**：派发条件改为 `if (result.ok && activeLevelPass && from && SIM_REF_ID[from])`。
- `activeLevelPass` 需在 `SimulatorPage` 持有：当前 `SimLevels` 已经在用 `SIM_LEVELS[activeLevelId].evaluate(ctx)` 算 `pass`（`ctx` 含 `metrics`/`bottleneck`），把该 `pass` 通过 state/ref 上提到 `SimulatorPage` 即可。
- 最低限度：先显式加 `result.ok`（虽失败已早退，写上更稳、意图更清）。

## 🆕 阻断级发现：capacity 不节流流量 → 第 4 关无解（原审查未覆盖）

**证据链：**
1. `simEngine.ts:197` `computeStep` 对加工/仓储节点：`outGood = inGood` —— **产能 `capacity` 不参与流量计算**，只用于瓶颈检测（`:424`）与 WIP 显示（`:442`）。
2. 流量守恒：`passed`（发货）≤ `total` = `batch × sourceCount`。默认单源 → `total = 200`。
3. `SimulatorPage.tsx:179` `simulate(nodes, edges, DEFAULT_BATCH)`，`DEFAULT_BATCH=200`（`simEngine.ts:54`）**硬编码**；全 `*.tsx` 检索 `batch` 仅在 `SimLog` 显示 `metrics.total`，**无任何调整 batch 的输入控件**。
4. `simLevelDefs.ts:99` 第 4 关要求 `passed ≥ 260`。

**判定**：在默认配置（batch 固定 200、单源、capacity 不节流）下，`passed` 最大 = 200 < 260 → **第 4 关在物理上不可通过**。
- 第 2 关 `passed≥200`：默认恰好 200（无不良时）边界通过，几乎无需优化。
- 第 3 关 `passed≥190` + 检验回流：默认 200 通过（只要加检验节点）。
- 第 4 关 `passed≥260` + "把瓶颈产能顶上去"：**既达不到 260，且"顶产能"在引擎里对班产零影响**（capacity 只影响检测/WIP，不改流量）。关卡优化目标与引擎模型脱节。

**修复方向（二选一，建议前者更贴近教学）：**
- **A. 让 capacity 真正节流**：在 `computeStep` 引入产能上限 `throughput = cap × SHIFT_HOURS`，节点实际流出 = `min(inGood, throughput)`（不足部分转为该节点 WIP/积压）。这样"顶瓶颈产能 → 班产上升"才成立，第 2/4 关 brief 才自洽。改动集中在 `computeStep` + 回流收敛（注意多轮迭代已天然支持积压）。
- **B. 不改引擎，调关卡语义**：把第 4 关改成"识别瓶颈 + 把瓶颈产能顶到 ≥ X 件/时，`passed` 保持 ≥200 即可"，阈值从 260 降到可达值。但这样"班产最大化"的爽点没了，且仍回避了 capacity 无效的问题。

**建议**：若要做"提产能→班产变高"的教学闭环，必须走 A；否则第 2/4 关的"优化"只是口号。

## 综合建议（按优先级）

1. **🆕 先修第 4 关无解**（高）：要么 A 让 capacity 节流，要么 B 把阈值降到可达值。否则第 4 关学生必卡死、且"提产能"教学点落空。
2. **P0 补 `sim_*` 判题练习**（高）：两岛打通的最后一环，否则差异化卖点悬空。
3. **P1 给默认节点合理的 `hours`/瓶颈模板**（中）：让 WIP/瓶颈可视化开箱即用。
4. **P2 关卡通过才回写闭环**（中）：派发加 `result.ok && activeLevelPass` 守卫。
