## 一、改造做对了什么（值得保留）

1. **把"数据矛盾"从 bug 改写成教学病灶**——这是本次改造最亮眼的设计。
   - 原 `WO-20260801-02`（计划 60 / 报工累计 49 / 工单 40）的"对不上"，现在被固化成正式题目：
     - 入库节点微练习 `9411`：「报工合格数合计 45，工单 qty_done 却是 40，按哪个数入库？」→ 教"先查清再入库"。
     - 自测题 `9215`：「WO-20260801-01 在 production_records 有报工但 qty_done=0，问题出在哪一步？」→ 教"状态机/released 不开工"。
   - 判题题 `#9311`（入库前对账）、`#9315`（完工数与报工汇总不一致的工单）已覆盖该差异，回归全部通过。
2. **新增 6 张业务表（采购/领料/销售/发货/客户/供应商）且病灶成链**：
   - 采购逾期（PO-3/7/10 承诺日已过、`arrive_date` 仍空）+ 短交（PO-4/9 到了但数量不足）→ 领料缺料（PK 中 4 行 `qty_issued<qty_required`）→ 工单开不了工，因果链完整。
3. **BOM 反算校验通过**：14 行 `pick_lists.qty_required` 全部等于 `ROUND(bom.qty_per * work_orders.qty_plan * (1+loss_rate))`，无一处拍脑袋。
4. **MRP 章节数值仍自洽**：已评审订单按产品汇总 = 减速机 290 / 伺服 200 / PLC 80 / 变频 80；轴承毛需求 1576 − 库存 1480 = 缺 96 套；控制主板 +68；与正文、自测题（9207/9208/9210）口径一致。
5. **跨岛打通做了命名空间隔离**：`simToSql.ts` 把仿真结果写入独立的 `sim_*` 三表，不碰 `dataset.sql` 的判题基准表，因此仿真回流不会污染哈希——架构上是对的。

## 二、🔴 P0：第 2 题判题哈希回归失败 —— ✅ 已修复（2026-08-09 17:30 复检）

> 原稿描述的"1 失败"状态已消除，以下为修复前的原始定位记录，供追溯。

`node scripts/gen-answer-hash.mjs --regress` 结果：**21 道真哈希题，20 通过 / 1 失败**。

| 项 | 内容 |
|---|---|
| 题号 | `#2 按车间统计在制工单负荷` |
| 题面 SQL | `SELECT workshop, COUNT(*) AS wo_count, SUM(qty_plan) AS total_plan FROM work_orders WHERE state='running' GROUP BY workshop ORDER BY workshop;` |
| 线上存储哈希 | `1a2401e5644e820fc7ea9cc755137ce561b74b1c17ecaa328f2ba54614c1e9ac` |
| 本地复算哈希 | `e39a109994e67f88c61d52e59395f99ae8e0f4a9d1159ae66c4a7d766fe13798` |
| 本地实际结果 | `["一号车间",1,100] ["三号车间",1,150] ["二号车间",1,60]` |

**根因**：跨岛共享工单 `WO-2026-001`（wo_id=8，`state='running'`，`workshop='一号车间'`，`qty_plan=100`）被静态写进了 `work_orders` 表，而 #2 按 `running` 聚合全表、未排除该 demo 工单，导致一号车间从"无"变成"1 单 / 100 台"，结果集改变 → 哈希失配。

**这是"加行也会动既有判题"的典型回归**，正是当初提醒过的风险。`dataset.sql` 第 306–310 行注释声称 WO-2026-001「不影响 c5/9302/9303/c4/c6」，但**漏算了 #2**（#2 属于原始 6 题 id 1~6，同样查 `work_orders` 全表）。该注释结论不成立。

**修复（最小且正确）**：
1. 把 #2 的 `answer_hash` 从 `1a2401e5…` 更新为 `e39a1099…`（即"含 WO-2026-001"的合法结果）。
   - 位置：`worker/src/migrations/seed.sql` 第 403 行；以及线上 D1 `sql_exercises` 表中对应行。
   - 复算命令：`node scripts/gen-answer-hash.mjs --sql "SELECT workshop, COUNT(*) AS wo_count, SUM(qty_plan) AS total_plan FROM work_orders WHERE state='running' GROUP BY workshop ORDER BY workshop;"` → 取打印的 hash 回填。
2. 修正 `dataset.sql` 第 306–310 行注释：删除"不影响 c5/…"的断言，改为说明"WO-2026-001 会进入所有对 work_orders/production_records/quality_checks/pick_lists 做全表聚合且未显式排除它的题目（含原始 #2），这些题的 answer_hash 需随本次扩展重算"。
3. 建议补充一道回归护栏：CI 中跑 `gen-answer-hash --regress`，任何一题 FAIL 即阻断合并。当前 20/21 通过，说明其余题都已被正确重算，仅 #2 漏网——护栏能防止下次再漏。

> 说明：#2 是否"应当"包含 WO-2026-001 是设计取舍。若希望 #2 只反映教学订单，可在题面 SQL 加 `AND wo_no <> 'WO-2026-001'` 并保留旧哈希；但更自然的是直接重算（demo 工单本就是 sandbox 里的真实在制单）。两种都行，关键是哈希与 dataset.sql 一致。

## 三、🟡 次要观察（不阻塞，建议跟进）

1. **WO-3 / WO-4 的差异未被显式教学**。5 张原始工单的 `qty_done` 与报工汇总全部不等（WO-1:0 vs 77、WO-2:40 vs 49、WO-3:0 vs 64、WO-4:90 vs 120、WO-5:80 vs 81）。目前只有 WO-1、WO-2 有微练习/自测覆盖，WO-3、WO-4 的差异学员在 `#9315` 里会看到但无处求证。对零基础学员，建议在采购/排产节点补一句"为什么这几张单的完工数和报工对不上"的引导，或明确告知"本数据集刻意保留多处差异，目的是练对账"。
2. **released 状态却带报工**（`WO-20260801-01`、`WO-20260802-01`）是状态机"病灶"，仅由 #9215 一处覆盖。零基础学员容易先入为主以为"有报工=已开工"。建议在 `work_orders` 表注释里点明这是刻意埋的坑，与教学节点对应，避免被当成数据错误。
3. **NULL / PLACEHOLDER 哈希题**：回归脚本只校验 `answer_hash` 非空且非 `PLACEHOLDER` 的题。若还有占位题计划转正，转正时必须用同一脚本复算，否则会上线即错。
