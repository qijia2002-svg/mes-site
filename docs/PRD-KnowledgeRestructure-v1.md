## 0. 三个必须先纠正的前提

在给结论之前，先纠正三条与任务书描述不一致的事实。它们直接改变重构方案。

### 0.1 线上是 19 个 topics，不是 20 个

实测：原生 3 个（id 1/2/3）+ 路线图 16 个（id 5000-5015）= **19**。章节总数 **54**（id 1-54，连续无空洞）。后续所有映射按 19/54 计算。

### 0.2 「四套重复」的说法不准确——真正重复的只有 500 和 502 两套

任务书判断是「500/501/502/503 四套同源重复」。实测正文后，结论要收窄：

- **501（30天冲刺）和 503（25天冲刺）不是重复项。** 它们在脑库里被完整保留为「冲刺变体」，目录名、阶段名、三件套结构（学习指南/实战作业/**每日任务**）与线上一一对应，零改动。用户自己的 index.md 写得很清楚：「1 主图 + **2 冲刺变体**」——那 2 个变体就是 501 和 503。
- **真正被合并掉的是 500 和 502**，它们合成了「主图」。

证据是结构级的，不靠推测：

| 脑库主图阶段名 | = rm-500 阶段名 | + rm-502 阶段名 |
|---|---|---|
| 阶段1_**职业全景**与**MES概念** | MES概念深化 | 实施职业全景 |
| 阶段2_**实施方法论**与**核心能力** | 实施方法论与平台 | 三大核心能力 |
| 阶段3_**核心模块配置**与**项目全流程** | 核心模块配置 | 项目全流程 |
| 阶段4_**实战交付**与**职业发展** | 项目实战 | 职业发展与出口 |

四个阶段名逐字是 500 与 502 的**拼接**。且脑库文件正文第一行自己写着：

> 「合并自《MES学习路线图·阶段1》+《实施工程师学习路线图·阶段1》。双线并进……」

映射是**确定的，不需要人工判断**。这让本次重构从「内容评估工程」降级为「一次确定性的数据迁移」，工作量下降一个量级。

### 0.3 500 与 502 的重复是「结构重复」，不是「正文重复」——这条决定了不能删正文

拉取 chapter 7（rm-500-1 学习指南）与 chapter 31（rm-502-1 学习指南）对比：

- chapter 7 讲 **MES 系统认知**：信息化金字塔、ISA-95、MESA 八大模块、精益+MES。
- chapter 31 讲 **实施工程师职业画像**：五条发展路径、招聘市场任职要求、四象限职业分析。

**两者内容零交集，是互补的两半。** 用户在脑库里做的是**并集合并**，不是删重。

更关键：脑库的合并稿是**有损压缩**。线上每份资源都带「推荐理由 / 学习方式 / 学习顺序建议 / 时长估算」，脑库合并稿把这些压成了要点清单 + 裸 URL 列表。

> **由此得出本次重构的第一原则：脑库提供的是「结构决策」，线上提供的是「正文资产」。合并结构、保留正文——绝不能用脑库合并稿直接覆盖线上章节，那会造成信息损失。**

## 2. 目标信息架构

### 2.1 结论：不加第四层。现有三层已经够用——因为 path↔topic 已经是多对多

关键实测发现：**路径 2 的 `topicIds` 是 `[1, 3]`，路径 1 是 `[1, 2, 3]`——topic 1 和 3 同时属于两条路径。系统已经支持一个 topic 被多条路径复用。**

这意味着脑库那两条正交的组织线（主题模块 / 求职路线）**不需要新实体就能表达**：

- **知识模块** = 承载 topic 的容器（常青知识，按学科分）
- **学习路线** = 引用若干 topic 的策展视图（目标导向，按时间盒分）

两者共用 `learning_paths` 表，只需一个 `kind` 字段区分。代价 = **1 个可空列 + 首页分区渲染**，而不是新增两张表、一套 API、一层路由。

## 3. 重复内容判定与依据

判定分三档，依据写明，不使用「疑似」。

### 3.1 真重复（结构级）—— 500 ↔ 502

**判定：重复。合并。**

依据三条，任一独立成立：
1. 脑库阶段名是二者阶段名的逐字拼接（§0.2 表）。
2. 脑库正文自述「合并自《MES学习路线图·阶段N》+《实施工程师学习路线图·阶段N》」。
3. 两条路径的用户画像描述几乎同义——500 是「有 MES 使用/运维经验，目标成为 MES 实施/配置工程师」，502 是「有 MES 使用/运维经验，目标成为专业实施工程师」。**同一个人、同一个目标、被给了两条入口，这就是重复的定义。**

注意重复发生在**导航层**：用户打开首页看到两条名字几乎一样的路线图（「MES 实施工程师学习路线图」vs「实施工程师学习路线图」），不知道该点哪个。这才是用户说「很多内容都是重复的」的真实所指。

### 3.2 非重复，误判风险最高的两处

**（a）501 与 503 不是重复。**
理由：脑库把它们完整保留为两个冲刺变体，一字未删。它们与主图是**时间盒 vs 知识深度**的关系，不是内容关系。503 还是基于真实简历（SCADA 运维 4 车间 + MES 设备联调 + PLC 现场）的定向版，脑库标注「优先级最高」。**误删 503 = 删掉用户求职命中率最高的那份资产。**

**（b）主图 4 阶段的三件套 ≠ 冲刺变体的三件套。**
主图是「学习指南 + 实战作业 + **知识作业**」，冲刺是「学习指南 + 实战作业 + **每日任务**」。第三件不同：知识作业考概念掌握，每日任务是排期打卡。**结构相似不等于内容重复**，两套都要留。

### 3.3 同题不同体裁 —— 线上 ch1-6 ↔ 脑库 MES/02-04

**判定：不是重复，但并列展示会制造重复感。合并进同一章，分区块。**

对比同题材料：

| | 线上 ch1「工单的生命周期与状态流转」 | 脑库 `MES/02_工单管理` |
|---|---|---|
| 体裁 | 教学稿 | 个人笔记 |
| 内容 | 三种工单来源、五个标准状态机、状态流转三条铁律、`work_orders` 表设计、可执行 SQL、`done_qty` 冗余字段的性能/一致性权衡 | 一句话理解、15 道工序拆单流程、奥来 AS-IS（线长在微信群发「今天做1000个KBO」）、TO-BE、`work_order` 表字段列表 |
| 视角 | 通用原理 | 我的现场 |
| 篇幅 | 长 | 短 |

**两份都有价值且不可互相替代**：线上教「行业上普遍怎么做」，脑库记「奥来现在怎么做、MES 化后怎么做」。

处置：**不新建并列章节，把脑库内容作为标注清晰的区块追加到线上对应章节末尾。**

```
ch1 工单的生命周期与状态流转
├── （线上原文：通用原理 + SQL）
└── 现场对应（奥来 AS-IS → TO-BE）      ← 脑库 MES/02 内容
```

这个处置不是折中，而是**直接实现用户自己定义的学习方法**——脑库 MES/index.md 原文：「每个 MES 模块：理论 → 奥来 AS-IS（现在怎么做） → TO-BE（MES化后怎么做）」。线上正文 = 理论，追加块 = AS-IS/TO-BE。三段式在一页里闭环。

映射：`MES/02` → ch1+ch2；`MES/03` → ch3+ch4；`MES/04` → ch5+ch6。

## 4. 进度迁移方案

### 4.1 核心设计：让迁移退化成一条算术规则

### 4.2 迁移规则

```sql
-- 规则 1：唯一映射规则
-- new_chapter_id = old_chapter_id - 24   (31 <= old_chapter_id <= 42)
-- 其余全部 chapter_id 不变

-- 规则 2：迁移前全量快照（可回滚）
CREATE TABLE progress_events_bak_kr1 AS SELECT * FROM progress_events;

-- 规则 3：执行映射
UPDATE progress_events
SET chapter_id = chapter_id - 24
WHERE chapter_id BETWEEN 31 AND 42;

-- 规则 4：冲突合并（用户对 7 和 31 都有记录时）
-- 语义为「或」：任一完成即完成
-- 同一 (user_id, chapter_id) 保留 status 最高的一条
--   completed > in_progress > started
-- 同级则保留 completed_at / created_at 最早的一条，其余删除
```

**结果：进度零丢失，且无需人工介入。** 用户在 rm-502 学过的章节，合并到主图后仍然算完成——这正是任务书要求的行为。

### 4.3 无法映射时怎么办

本次设计下**不存在无法映射的记录**（12 条全部一一对位）。但规则必须为未来定义：

1. **不删除。** 任何无法映射的 `progress_events` 记录写入 `progress_archive` 表，保留 `original_chapter_id`、`original_topic_id`、归档原因、归档时间。
2. **不展示。** 前端进度计算忽略 `progress_archive`，避免分母污染导致完成率虚高或倒退。
3. **可申诉。** 归档记录保留 12 个月；若后续该章节以新 id 重新上线，可按 `original_chapter_id` 反查回填。
4. **完成率口径变更须显式告知。** 若归档导致某路径完成率数字下降，路径页顶部展示一次性说明条（文案：「本路径已合并去重，原 XX 条学习记录已迁移」），点击关闭后不再出现。**不允许静默变更用户看到的完成率数字。**

### 4.4 章节与主题的下线方式

- **一律软下线**：`status = 'archived'`，禁止 `DELETE`。
- 归档对象：path 502；topic 5008-5011；chapter 31-42。
- 归档章节的正文在并入 ch7-18 **之后**才置 archived，顺序不可颠倒。
- 老 URL（`/paths/rm-502/...`）返回 **301 重定向**到 `/paths/rm-500/...` 对应位置，不返回 404。

## 5. 五个核心问题的逐条结论

### 问题 1：线上现有内容怎么处理？

**结论 1.1 — 保留哪些、合并哪些、下线哪些**

- **保留原样（36 章）**：ch1-6（原生，质量最高）、ch19-30（501）、ch43-54（503）。
- **合并（12 章存活 ← 24 章输入）**：ch7-18 吸收 ch31-42 正文，做**并集拼接**，不是二选一。因为 §0.3 已证明两者内容零交集，删任一半都是内容损失。
- **下线（12 章）**：ch31-42，正文迁移完成后归档。
- **绝不做**：用脑库合并稿覆盖线上正文。脑库稿丢失了「推荐理由 / 学习方式 / 学习顺序 / 时长估算」，是有损压缩版。脑库稿只贡献〈阶段目标〉〈关键认知清单〉〈完成标志〉三段，作为章节导语和自检清单。

**结论 1.2 — 进度怎么迁移**

一条规则：`chapter_id ∈ [31,42] → chapter_id − 24`，其余不变。冲突取「或」（任一完成即完成，保留最早完成时间）。零丢失、零人工。详见 §4。

**结论 1.3 — id=1 / id=2 与脑库 MES//SQL/ 的关系**

明确立场，三条：

- **id=1 与脑库 `MES/`：合并，线上为主。** 线上正文是原创教学稿（状态机、表设计权衡、可执行 SQL），脑库同题是个人笔记（一句话理解 + 奥来现场）。**线上做主干，脑库做「现场对应」追加区块。** 脑库独有的 05-08（质量/追溯/设备/看板）作为新 topic 补进 M2。
- **id=2 与脑库 `SQL/`：并存，分工不同，脑库为主干。** id=2 无自有章节（`topicIds: [1,3]`，是策展视图），它教的是「排查方法」；脑库 SQL/ 教的是「SQL 语法基础」，线上完全缺失。**脑库 SQL 02-05 新建为 M3 知识模块（主），id=2 保留为学习路线（从），复用 M3 的 topic + topic 1/3。** 靠已有的多对多能力实现，不复制内容。
- **谁是主：知识模块是主，学习路线是从。** 章节正文只存在于知识模块与主路线图下；学习路线只做引用和排序，永不持有正文副本。**这是防止未来再次产生重复的根本约束**——四套路线图重复的根因就是每条路径都复制了一份自己的内容。

### 问题 2：网站信息架构应该是几层？

**结论：维持三层。引入「模块 / 路线」区分，但用一个字段实现，不加第四层。**

理由：**系统已经支持多对多**（path 2 与 path 1 共享 topic 1、3，实测确认）。脑库那两条正交组织线可以直接映射为：

| 脑库概念 | 网站实体 | 实现 |
|---|---|---|
| 主题模块（ERP/MES/SQL） | `learning_paths` where `kind='module'` | 持有 topic 与正文 |
| 学习路线（主图 + 冲刺） | `learning_paths` where `kind='route'` | 引用 topic，不持有正文 |

**代价（这是真实成本，不是零）**

| 层面 | 改动 | 量级 |
|---|---|---|
| DB | `learning_paths` 加 `kind VARCHAR(16) DEFAULT 'route'`；`chapters` 加 `practice_link TEXT NULL`（供问题 4） | 2 个可空列，无数据迁移 |
| API | `/learning-paths` 增加 `kind` 字段与可选过滤参数；其余端点签名不变 | 1 个端点小改，向后兼容 |
| 页面 | 首页从「一个路径列表」改为「两个分区列表」；模块卡片显示章节数，路线卡片显示阶段数与时间盒 | 1 个页面 |

**对比新增实体方案**（新建 `knowledge_modules` 表 + 一套 CRUD + 新路由 + 与 paths 的关联表），后者约 5-8 倍工作量，且引入「一个 topic 到底归模块还是归路线」的归属歧义。**不值得。**

**若坚持不加 `kind` 字段的退路**：用 `slug` 前缀（`m-*` / `r-*`）+ 前端硬编码分组。能跑，但分组规则散落在前端、无法后台配置。**不推荐，仅作为紧急降级方案。**

### 问题 3：四个空目录怎么办？

**结论：不留入口。四个减为三个，降级为无交互的纯文本清单。**

- **先减一个**：「质量」不是空模块，`MES/05_质量管理` 已有内容。取消其独立模块资格，归入 M2。（§3.4）
- **剩下 PLC / PowerBI / AI：不建 path，不建 topic，不给点击入口，不给进度条。** 仅在知识模块区末尾以一行灰色文本呈现：「规划中：PLC ／ PowerBI ／ AI」。

**空入口是噪音，不是激励**，三条依据：

1. **它稀释完成率。** 4 个空模块进 IA，整站完成率立刻被稀释；用户什么都没少学，数字却掉了。对单人自学产品，进度数字是核心正反馈，不能拿它换一个空壳。
2. **它撤销本次重构的成果。** 本次重构的全部目的是「点进去发现内容重复」→ 修好。加空入口 = 制造「点进去发现没内容」，这是同一类信任损伤的另一个版本。
3. **它必然违反 P0 规则。** 空模块页只能填「敬请期待」「内容建设中」——正是 P0 明令禁止的空洞占位文案。**不存在合规的空状态页写法。**

**升级阈值（明确可判定，避免反复讨论）**：任一目录**落地 ≥3 个 md 文件且都有正文**时，自动升为正式知识模块并获得入口。低于 3 章不升级——2 章的模块点进去仍然是失望。

### 问题 4：与「工艺路线搭建器」怎么衔接？

**结论：双向链接，但两个方向不对等。「章节 → 搭建器」常驻；「搭建器 → 章节」仅在卡住时出现。**

映射关系（搭建器关卡 ↔ M2 章节）：

| 关卡 | 主题 | 关联章节 |
|---|---|---|
| L1 | 工单 | ch1 ch2 + 脑库 MES/02 现场对应块 |
| L2 | BOM | ch3 ch4 + 脑库 MES/03 |
| L3 | 报工 | ch5 ch6 + 脑库 MES/04 |
| L4 | 质检 | T-NEW-2 质量管理（脑库 MES/05） |
| L5 | 返工 | T-NEW-2 质量管理 + T-NEW-3 追溯管理 |
| L6 | 综合 | R1 阶段3（ch13-15） |

**方向 A：章节 → 搭建器（常驻）**
章节正文末尾固定位置放练习入口，深链到对应关卡。文案指向具体动作，例如「在搭建器 L1 里跑一遍工单状态流转」。实现 = `chapters.practice_link` 字段。

**方向 B：搭建器 → 章节（条件触发，不常驻）**
仅在用户**同一关卡失败 2 次**或**停留超过 3 分钟无操作**时，出现「回看原理」链接。

**为什么不对等——这是刻意的，不是省事**：搭建器是「练」，章节是「讲」。**练是主战场，讲是补给。** 关卡里常驻一个回看链接，等于持续邀请用户在遇到难点时逃回阅读——阅读体感轻松、进度看起来在动，实际是回避了练习。**卡住时才给，才是补给；随时都给，就是逃生口。**

（同理，这些入口用文字标签，不用 emoji 图标，遵循 P0 规则；图标走统一 SVG 图标库，具体选型由架构师锁定。）

### 问题 5：「知识重构是 Markdown 导入的第一个真实用例，两者合并考虑」这个判断成不成立？

**结论：方向对，但作为排期决策不成立。必须拆成三批。**

**成立的一半**：脑库有 67 个文件且会持续更新，手工搬运不可持续。**未来的内容同步必须走导入功能**，这个判断完全正确，也应该成为导入功能的需求来源——导入功能的验收标准就该用脑库真实文件跑通，而不是用造的样例。

**不成立的一半**：**本次重构的主体工作，导入功能一行代码都帮不上。**

拆开看本次重构的动作构成：

| 动作 | 占比 | 导入功能能否覆盖 |
|---|---|---|
| 合并 500+502 正文 | 大 | **否** —— 是存量两份正文的拼接，不是新文件导入 |
| 重命名 4 条路径 + 12 个 topic | 中 | **否** —— UPDATE 语句 |
| 下线 1 条路径 + 4 topic + 12 章节 | 中 | **否** —— 状态变更 |
| 进度迁移 + 冲突合并 | 中 | **否** —— 数据迁移脚本 |
| 灌入脑库新增 17 章 | 小 | **是** —— 这才是导入的用武之地 |

**导入功能解决「新增内容」，不解决「存量去重」。** 本次重构 80% 是后者。

**更硬的一条：顺序反了会返工。** 若等导入功能做好再动结构，导入时面对的仍是 500/502 并存的旧结构——**要么导入到错误的结构里事后再迁移一次，要么导入功能被迫内建一套只用一次的合并逻辑。** 两条都是浪费。

**正确顺序：先把地基修正，再往上盖。**

- **B1 结构重构**：一次性 SQL migration，**不依赖导入功能**，独立可交付。
- **B2 导入功能**：需求输入来自 B1 暴露的真实格式问题（frontmatter 解析、wikilink `[[...]]` 转换、目录层级映射为 path/topic/chapter、**标题 emoji 剥离以符合 P0**）。B1 先做，B2 的需求才准确。
- **B3 内容灌入**：用 B2 导入脑库新增 17 章。

**修正后的判断：知识重构不是导入功能的第一个用例，而是导入功能的需求来源。** 这个区别决定了先后顺序——需求来源必须在功能之前。

## 6. EARS 格式验收标准

**结构合并**
- **当** B1 迁移脚本执行完成 **时**，系统**应**使 `/api/v1/learning-paths` 返回 7 条记录，其中 `id=502` 的 `status` 为 `archived`。
- **当** 用户访问路径 500 的阶段1 **时**，系统**应**在同一页面同时呈现「实施工程师职业全景」与「MES 概念深化」两部分内容。
- **若** 章节 7-18 的任一正文字符数小于合并前 500 侧原文字符数，**则**系统**应**判定迁移失败并中止后续步骤。

**进度迁移**
- **当** 迁移脚本执行 **时**，系统**应**将所有 `chapter_id` 介于 31 与 42 之间的 `progress_events` 记录的 `chapter_id` 减 24。
- **若** 同一用户在合并后的同一 `chapter_id` 上存在多条记录，**则**系统**应**保留状态最高的一条，同级时保留时间最早的一条。
- **当** 用户在合并前于 rm-502 任一章节标记完成 **时**，合并后系统**应**在主路线图对应章节展示为已完成。
- **当** 迁移完成 **时**，系统**应**保证迁移后进度记录去重总数不小于迁移前的去重总数。
- **若** 存在无法映射的进度记录，**则**系统**应**将其写入 `progress_archive` 并保留原始 `chapter_id`，**且不得**执行删除。

**信息架构**
- **当** 用户访问首页 **时**，系统**应**将路径分为「知识模块」与「学习路线」两区分别展示。
- **在** `kind='route'` 状态下，系统**应**仅引用 topic，**不得**持有独立的章节正文副本。
- **当** 客户端请求 `/api/v1/learning-paths` 且未传 `kind` 参数 **时**，系统**应**返回全部已发布路径，保持与重构前的向后兼容。

**旧链接**
- **当** 用户访问任一 `rm-502` 下的旧 URL **时**，系统**应**返回 301 重定向至主路线图对应位置。
- **若** 归档章节无对应新位置，**则**系统**应**重定向至所属路径首页，**不得**返回 404。

**空模块**
- **在** PLC / PowerBI / AI 尚未落地内容的状态下，系统**应**仅以纯文本呈现其名称，**不得**提供可点击入口或进度条。
- **当** 任一规划中目录落地 3 个及以上含正文的章节 **时**，系统**应**允许将其升级为正式知识模块。

**搭建器衔接**
- **当** 用户阅读至具备 `practice_link` 的章节末尾 **时**，系统**应**展示指向对应关卡的练习入口。
- **当** 用户在同一关卡失败达 2 次 **时**，系统**应**展示指向关联章节的回看入口。
- **在** 用户未触发失败条件的状态下，搭建器界面**不得**常驻展示回看章节入口。

**P0 合规**
- **当** 任何章节内容经导入或迁移写入 **时**，系统**应**剥离标题中的 emoji 字符（脑库现存 `📚` `🗺️` `🚀` 等）。
- **在** 任何页面状态下，系统**不得**使用 emoji 作为功能图标，**不得**使用紫色至粉色渐变，**不得**出现「敬请期待」「内容建设中」类空洞占位文案。
