# PRD v1：零基础学习者重构（MES 实训平台）

> 作者：许清楚（PM） 日期：2026-08-08 状态：v1.1（已按用户决策修订）
> 触发：用户原话「这个学习的知识我感觉很不好，能不能重新设计一下，方便我更容易理解，更容易学习」
> **v1.1 修订**：用户决定**不使用生活化比喻**，改走「真实业务数据例子 + 术语点即解 + 渐进路径 + 互动反馈」四杠杆。原「统一比喻体系」决策作废。阶段划分待用户给定，本文档仅提供决策输入。

## 一、用户画像（主要）

**「转岗小陈」** — 25-35 岁，非制造、非 IT 背景（文员/销售/应届生），因转岗或兴趣接触制造业数字化。
- 已知：会用 Excel，看得懂中文业务文字
- 未知：不知道工单/BOM/齐套/报工是什么，没写过 SQL，没进过车间
- 场景：晚上或周末，每次 15-30 分钟，手机或笔记本
- 放弃点：连续 2 屏看不懂就关页面；SQL 编辑器空白光标闪烁时直接跳过
- 成功定义：能对同事讲清「一张订单在工厂里怎么走完」

**次要画像**：制造业一线转数字化岗（懂车间不懂系统）——他们有实物直觉，缺系统抽象，可跳过铺垫直接进结构。

## 二、核心问题陈述

现有内容是**给从业者写的参考资料，不是给新手写的教材**。已核实证据（`docs/seed-content-v1.json`，6 章，1255-1691 字/章）：首章《工单的生命周期与状态流转》开篇即用 ERP、MRP、排产、领料、报工、在制、成本归集、财务口径、状态机等术语，全篇无一个具体例子、无中途自测点。零基础读者第一段就掉队。

四个具体断裂：
1. **密度与抽象**：术语密集连续散文，无分段消化点（违反 chunking / segmenting）
2. **无起点**：12 节点工厂全景一次性铺开，没有「先走哪条」的唯一入口（选择过载）
3. **知识零散**：章节各讲各的，不回指全局，学完不知道彼此关系（无 schema 锚点）
4. **SQL 悬崖**：从「读文字」直接跳到「空编辑器写查询」，中间无过渡（缺 worked example → completion 阶梯）

### 3.0 实战完成度口径（产品决策，回应架构侧 BLOCK-02 / BLOCK-03）

**问题**：12 个节点每个都挂了 sql 资源。若「算完成」一律要求做完 SQL，那么**无论用户怎么划阶段，第一阶段都会立刻撞上全平台最硬的门槛**，「由浅入深」当场失效。这是本次要解决的四大痛点里「SQL 门槛高」的直接成因。

**决策一（完成度口径按阶段配置）**：采纳架构侧 `flow_stages.practice_types` 方案。

| 阶段 | practice_types | 说明 |
|---|---|---|
| **入门阶段（第一阶段，无论用户如何命名与划分）** | `["micro","quiz"]` | SQL 入口照常可见可做，但**不计入完成度**；学有余力的可做，零基础的不被挡 |
| 后续阶段 | 默认全集（含 `sql`） | SQL 计入完成度 |

这是**阶段级配置，不是给 36 条资源逐条打标**——内容侧可直接改，无需开发介入。

**决策二（两个机制必须配合，否则出现断崖）**：入门阶段不计 SQL、下一阶段突然全量计入，中间会形成难度断崖。缓冲由 F6 三阶梯承担——SQL 首次计入完成度时，学习者是从「看例题」阶起步的，不是直接面对空编辑器。**两者必须同时存在**：只有 practice_types 没有三阶梯，断崖仍在；只有三阶梯没有 practice_types，第一阶段照样被卡死。

**决策三（入门阶段宜小）**：正因入门阶段不计 SQL，它不宜过大。建议控制在 4-5 个节点内，否则学习者会在无 SQL 状态下滑行过久，进入下一阶段时落差更大。此条作为用户划分阶段时的参考约束。

**决策四（下一步指向必须限定在阶段内，BLOCK-03）**：F1 主 CTA 与 F2 的「下一站」取值必须**在当前阶段内取**，不得走全局拓扑序。否则学习者完成入门阶段首个节点后，会被直接带到另一个阶段的节点，F1/F2 验收标准直接失效。

### 3.1 易懂性四杠杆（替代原比喻方案）

用户决定不走生活化类比。四条杠杆合起来承担同样的降门槛职责：

| 杠杆 | 落点 | 为什么能替代比喻 |
|---|---|---|
| **真实业务数据例子** | F3 | 用领域内的具体实例做「具象化」，而不是用领域外的类比。具象化的效果来自「可指认」，不来自「像什么」 |
| **术语点即解** | F4 | 术语是零基础的主要外在负荷来源，就地消解，不必先建一套替代词汇 |
| **渐进路径** | F1 / F2 / F5 | 控制内在负荷的进入节奏（分块 + 由简到繁） |
| **互动反馈** | F6 / F7 / F8 | worked example 渐隐支架 + 检索练习，靠做中学建立结构 |

**这个替换在学习科学上站得住，不是妥协。** 比喻的作用是把新知识绑到已有记忆上，但它有已知代价——**类比迁移失真**：学习者会把类比的属性过度外推。例如把 BOM 说成「配方」，恰恰会强化「BOM 就是一张平铺的清单」这个错误认知，而 BOM 的关键性质是**层级和用量**。用真实 BOM 记录（含 `qty_per` 与 `loss_rate`）当场演示，比任何配方类比都准确。**误解澄清（misconception）槽位因此从辅助升级为主力手段**，承接原本由比喻承担的「打通直觉」职责。

### 3.2 给用户做阶段划分的决策输入（本节不锁定方案）

阶段怎么切由用户定。以下是我从代码里核出的事实，供决策参考：

**事实一：现有 `phase` 字段是业务分组，不是难度分组。** `factoryFlow.data.ts` 真实 12 节点分布为 plan 7 个 / production 2 / qc 1 / logistics 2。

**事实二：最抽象的两个概念排在很靠前的位置。** 若照业务流顺序，学习者在第 3-4 站就遇到主生产计划（MPS）与物料需求计划（MRP）——全流程仅有的两个「算出来的」概念，此时他还没见过任何实物环节。

**事实三：节点的具象程度差异很大。**
- 看得见摸得着：客户下单、领料发料、车间执行、质量检验、生产入库、发货出库
- 居中：订单评审、生产派工、BOM 与工艺路线、采购与供应商
- 纯计算：主生产计划、物料需求计划

**供参考的一个方向（非锁定）**：让前几站集中在具象节点先把骨架立起来，把 MPS/MRP 放到靠后位置，等学习者有了实物挂靠点再讲。若采纳「先具象后抽象」，全景图上会出现节点跳跃（例如从客户下单直接跳到车间执行），此时**必须**配一句明示，如「先认识几个最看得见的环节，中间的后面补上」——没有这句话，跳跃会被读成缺陷；有了它，跳跃变成承诺。

**事实四（划分方式会影响开发成本，来自架构侧验算）**：现有 `sort` 值若在阶段内保持业务流顺序，则**不需要新增排序列**——阶段内按 `sort` 升序即可得到正确学习序。但**如果用户希望在同一阶段内打乱业务流顺序**（例如先讲领料、再讲 BOM），就必须新增 `learn_sort` 列，并承担 `sort` 与 `learn_sort` 长期不同步的数据漂移风险。

结论：**跨阶段重排是免费的，阶段内重排是要付成本的。** 请在转述给用户时带上这条——它可能影响他怎么切。

待用户给出划分后，我再出「每站收哪些节点」的细案。

### 3.5 SQL 三阶梯的三条内容铁律（写入内容规范）

1. **`worked_sql` 不得等于 `answer_sql`。** 「看例题」阶要给的是**同类已解决的例子**，不是本题答案。两者相同的话，三阶梯退化为「直接看答案」，F6 的教学意义归零。架构侧已加 CI 门禁断言。
2. **挖空版（completion）必须人工撰写**，不由 `answer_sql` 运行时自动生成。挖哪个空是教学决策——要挖在本题真正的认知难点上，自动生成只会挖在语法位置上。
3. **「看例题」一键运行不得标记节点完成。** 范例本来就带答案，跑一下就算完成的话，点个按钮进度就涨。sql 只在「自己写」阶通过后才计入完成。

第 3 条直接对应竞品调研里的核心差评：DataCamp 被批「计分过松，点开答案也给分」，导致学习者刷参与度而非刷理解。这是我们明确要避开的失败模式，不是边角细节。

### 3.3 内容素材：数据集已具备一条可直接用的完整因果链

我核过 `web/src/features/sql-sandbox/dataset.sql`（12 张表）。**数据集本身已经埋好了一条跨 5 张表、算得通的真实业务链**，这是「不用比喻」路线最有价值的现成资产：

| 环节 | 真实记录 | 数字 |
|---|---|---|
| 客户订单 | `SO-20260725-01` | 伺服电机 SM-80，60 台，交期 2026-08-15 |
| 工单 | `WO-20260801-02` | 计划 60，已完成 40，状态 running，二号车间 |
| BOM | product 2 → material 3 | 单台用量 1，损耗率 3% |
| 物料需求 | 60 × 1 × 1.03 = 61.8 | **→ 需求 62，与 `pick_lists.qty_required` 完全对上** |
| 领料 | `PK-20260804-01` | 需求 62，实发 40，状态 partial |
| 结果 | 工单卡在 40 台 | 实发量正好卡住产出量 |

这条链能一路讲通「订单怎么变成工单、BOM 怎么算出用量、为什么损耗率不能忽略、缺料如何直接卡住产出」，**全程不需要任何类比，因为每一步都能指着一条真实记录说「就是它」**。建议把它定为贯穿多个节点的主线案例。

**F3 的关键约束：章节里举的例子，必须就是该节点 SQL 练习要查的那几条记录。** 读的时候见过 `WO-20260801-02`，练的时候查的还是它，学习者不用在两套虚构情境之间切换——这直接对应认知负荷研究里的**分割注意力效应**（信息源分散会白白消耗工作记忆）。

**一处待确认（不是结论）**：`work_orders.qty_done` 与 `production_records` 的报工汇总之间，我抽查到疑似对不上的情况（WO-2 的 `qty_done=40`，而抽样到的两条报工记录 `qty_ok` 为 25 与 20）。我只看到前 4 条报工记录，未穷举，**不能断定是数据缺陷**。鉴于该数据集本就有意「埋病灶」，这可能是刻意设计的排查案例。**建议架构师核一次全量**：若是刻意的，它是极好的教学素材（「报工汇总和工单完成数对不上，怎么查」）；若是无意的，会让零基础学员困惑。两种情况处理方式相反，需要先定性。

### 3.4 内容素材的一个事实更正

数据集的产品是**工业设备**——减速机 XJ-200、伺服电机 SM-80、PLC 控制器 FX-3U、变频器 VF-15K；物料是铸铁箱体、轴承、定子组件、控制主板。此前拟定的「保温水杯工厂」比喻与真实数据领域完全不符，一旦落地会造成读章节与做练习**产品对不上**的割裂。除用户决策外，这也是该比喻方案本就应当废弃的独立理由。

## 四、明确不做（Out-of-Scope）

| 不做项 | 原因 |
|---|---|
| 生活化比喻体系 | 用户明确不要；且类比迁移失真会强化错误认知（如「BOM＝配方」掩盖层级与用量），改由真实数据例子承担具象化职责 |
| 重写全部 12 节点内容 | 先重写首个阶段验证方法论有效，避免一次性重写后方向错误导致全量返工 |
| 视频课程 | 制作与维护成本远超 MVP，且当前痛点是「看不懂文字」，换介质不解决讲解质量问题 |
| AI 对话式答疑助手 | 讲解本身没讲清时，加 AI 只是掩盖问题；应先把内容改对，且答疑质量不可控 |
| 社区/评论/排行榜 | 无用户规模，冷启动下空评论区反而制造挫败感 |
| 证书与考试认证 | 学习效果尚未验证，过早发证损害可信度 |
| 连胜打卡（streak）与积分体系 | 竞品证据显示这类机制易导致「刷参与度不刷理解」（DataCamp 差评核心）；MVP 先解决理解，不做上瘾机制 |
| 拖拽搭建（simulator）改造 | 属于进阶体验，主线不依赖它，保持现状即可 |
| 移动端原生 App | 现有响应式 Web 已覆盖目标场景（晚间碎片时间） |
| 多语言 / i18n | 目标用户为中文母语学习者 |
| 领域模型统一（factoryFlow 与 simTypes 合并） | 技术债，与本次学习体验重构无因果关系，另行排期 |

## 六、竞品标杆与学习科学结论

**直接竞品**
| 竞品 | 做对了什么 | 差评暴露的坑（我们要避开） |
|---|---|---|
| Codecademy | 浏览器内即时判分；小步递进不一次性倾倒信息 | 「过度牵手」——步骤铺太满，概念记不住；指令含糊反而卡住新手；Trustpilot 仅 2.4/5 |
| DataCamp | 小块课程 + 清晰路径分层，Trustpilot 4.6/5 | 「80% 代码预写、只填 20%」导致概念不内化；计分过松，点开答案也给分 |
| Khan Academy | 概念先于语法，先讲「为什么这样做」；掌握度达标才放行 | 游戏化偏重；编程内容深度有限 |

**替代方案**
| 替代 | 特点 | 对我们的启示 |
|---|---|---|
| SAP Learning（原 openSAP 2024 已合并） | 官方 learning journey，术语与流程逻辑讲得系统 | 能讲清「一张采购单怎么流」，但**缺练习环境**——正是我们 SQL 沙盒的差异化 |
| Duolingo | 首次打开 1 分钟内完成第一个练习，无需注册 | 借鉴「立刻能做一件事」，不借鉴 streak/排行榜（见 Out-of-Scope） |

**学习科学结论（映射到功能）**
1. **认知负荷理论**：工作记忆容量固定，需削减外在负荷、分级内在负荷 → F5、F2
2. **worked example → completion → free problem**（渐隐支架）：对无图式的新手，探索式学习效率极低，工作记忆全耗在找路径上 → F6，这是 SQL 门槛的正解
3. **具象化建 schema**：抽象概念需绑定到可指认的具体实例。**本项目采用领域内真实记录，而非领域外类比**——既达成具象化，又规避类比迁移失真 → F3 + 3.3 主线案例
4. **分割注意力效应**：信息源分散会白白消耗工作记忆 → 章节例子与 SQL 练习必须用同一批记录（F3 约束）
5. **先整体后局部**：先给全局结构再填细节 → F2（具体划分待用户定）
6. **检索练习 / 测试效应**：低风险小测比重读更能巩固，并暴露理解缺口 → F8
7. **专长反转效应**：对新手有效的高支架对熟手有害 → 支架必须可跳过（F6 阶梯允许跳级），照顾次要画像

## 七、非功能与合规约束

- 图标：一律走 `web/src/components/Icon.tsx` 注册表（已含 chapter/quiz/sql/hint/success/error/help 等），**禁止 emoji 作功能图标**；提示用灯泡图标（`hint`），正确用对勾圆圈图标（`success`），错误用叉号圆圈图标（`error`）
- 配色：仅用 `design-system/design-tokens.css` 既有 token（森林绿 `--accent: #547C70`），**禁止紫→粉渐变**，禁止硬编码 hex
- 文案：全中文口语化，**禁止 Lorem ipsum / Welcome to 类空洞占位**
- 措辞：比喻/误解/讲解一律归 `node_explainers`（表述为「节点的讲解」），**不进 `node_resources`**，避免污染进度派生（ADR-017）
- 性能：章节首屏 < 3s；SQL 沙盒为浏览器内 sql.js，无需后端往返
- 埋点：`chapter_opened`、`chapter_completed`、`quiz_submitted`、`sql_stage_advanced`、`hint_revealed`、`path_started`
